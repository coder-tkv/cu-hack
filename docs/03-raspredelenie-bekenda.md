М# Распределение бекенда на троих (4 часа)

Из плана убрано всё, что не влияет на главную цепочку: настоящий лог → факты кода → доказательства → рекомендация → скачиваемое правило.

## Кто что делает

### Бек-1: данные (парсер)

Остаётся на беке до конца.

- `schemas/events.py` и `parsers/claude_code.py`.
- Построчное чтение с `source_line` и индексом блока в `step_id`.
- Связь tool_use и tool_result по id.
- Запись `user` с `tool_result` не считается человеком.
- Битая или оборванная строка даёт warning, неизвестный тип даёт `unknown`, отсутствующие поля дают `null`.
- `analysis/usage.py`: токены с дедупликацией по message id, без денег.
- Во второй фазе (с ~1:30): `reports/builder.py` и `exporters.py` (`report.md`, `CLAUDE.generated.md`, `report.json`).
- Тесты парсера и usage.

### Бек-2: детекторы

Самая тяжёлая роль, её отдаём самому сильному в алгоритмах.

Порядок по приоритету:

1. `metrics.py`: счётчики, `errors / known_status`, `null` не равно `0`.
2. `failures.py`: `is_error`, exit code, цепочки повторов.
3. `repeats.py`: только точные повторы, окно 15, порог 3.
4. `interventions.py`.
5. `timing.py`: интервал больше 60 с, формулировка «интервал без записей».
6. `ranking.py`.

Если успеваем: `edits.py`, только точный откат Edit `A→B→A`, иначе «недостаточно данных».

Каждое из шести направлений возвращает явный результат, даже пустой.

### Бек-3: платформа

Переходит на фронт после того, как дизайнер закончит.

- Pydantic-схемы `findings.py` и `reports.py`. Это контракт, от него зависят все.
- SQLite из 3 таблиц: `sessions`, `steps`, `analyses` (отчёт как JSON-блоб).
- API:
  - `POST /api/sessions`
  - `GET /api/analyses/{id}`
  - `GET /api/analyses/{id}/report`
  - `GET /api/sessions/{id}/steps` (с пагинацией)
  - `GET /api/sessions/{id}/steps/{step_id}`
  - скачивание артефактов по allowlist
- `jobs/runner.py`: последовательный пайплайн `parsing → analyzing → explaining → assembling` со статусами.
- При падении LLM отчёт получает статус `partial`. При старте зависшие `running` переводятся в `interrupted`.

### ML (часть бека, границы зафиксированы, чтобы никто не пересекался)

- `context_builder`, промпт, `llm/client.py` с `explain(packet)`, `validator.py`.
- Простое маскирование секретов регулярками.
- Шаблонные `rule_based`-рекомендации как запасной вариант.

## Таймлайн

| Время | Что происходит |
|---|---|
| 0:00–0:30 | Вся команда: берём настоящий лог, замораживаем контракты (`Step`, `Candidate`, JSON отчёта), делаем скелет репо. Бек-3 отдаёт мок-отчёт для фронта, Бек-1 отдаёт fixture из шагов. |
| 0:30–1:45 | Параллельная работа. Бек-2 сначала сидит на fixture, потом переключается на реальный парсер. Бек-3 к 1:00 должен отдавать мок через API. |
| ~1:45 | Дизайнер закончил → Бек-3 уходит на фронт. Его недоделки забирает Бек-1. |
| 1:45–3:00 | Сборка сквозной цепочки на реальном логе. Фронт подключается к API. |
| 3:00 | Feature freeze. |
| 3:00–3:40 | Второй, незнакомый лог, баги, честные состояния (`partial`, `insufficient_data`). |
| 3:40–4:00 | Репетиция демо и питча, запасная запись демо на случай сбоя. |

## Точки стыка

Тут обычно всё ломается, поэтому договариваемся о них в первые 30 минут.

- Парсер отдаёт `Step` детекторам.
- Детекторы отдают `Candidate` ML-части.
- ML возвращает валидированные judgments в runner.
- Builder собирает контракт отчёта для фронта.

## Что вырезаем

- Codex.
- Близкие повторы через `SequenceMatcher`.
- Стоимость в деньгах.
- `DELETE` и retention.
- Idempotency и кэш.
- Повторный анализ.
- Cookies и CSRF.
- Выбор сессии из нескольких (только предупреждение).
- Фильтры, графики и история загрузок на фронте.

## Фронт после перехода Бека-3

Только три экрана: загрузка, статус (опрос раз в 2 с), отчёт. В отчёте карточки находок, метрики, просмотр доказательств по `step_id` и кнопки скачивания.

## Главный риск

Бек-2 может стать узким местом. Если к 1:30 у него готовы только метрики, ошибки и повторы, то `edits` и `timing` сразу превращаем в честное «недостаточно данных». Три качественных детектора лучше шести сырых.
