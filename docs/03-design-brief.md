# Бриф для дизайнера: «Что наделал агент»

> У нас **4 часа** на дизайн. Этот документ написан под это ограничение.
> Правило: **лучше два экрана, доведённых до конца, чем шесть набросков.**
> Раздел [«План на 4 часа»](#0-план-на-4-часа) — главный. Всё остальное — справка.

Контекст продукта целиком: [01 — простыми словами](01-problema-prostymi-slovami.md), [02 — архитектура](02-architecture-and-ml.md).

## 0. План на 4 часа

Делаем **2 экрана и 1 раскрывающийся блок**. Не 4 страницы. Отдельной страницы просмотра шагов нет — доказательства раскрываются прямо внутри карточки находки.

| Время | Что делаем | Результат |
|---|---|---|
| 0:00–0:30 | Мини-система: цвета, шрифты (обычный + моноширинный), 3 регистра «факт / гипотеза / нет данных», бейджи статусов | Стайл-тайл на одном артборде |
| 0:30–1:00 | **Экран 1. Загрузка** + состояние обработки в том же экране | 1 артборд, 3 состояния |
| 1:00–2:30 | **Экран 2. Отчёт** — шапка, метрики, список находок | 1 артборд, главный |
| 2:30–3:15 | **Карточка находки в раскрытом виде** — доказательства, шаги лога | Компонент + 1 состояние |
| 3:15–3:45 | 3 обязательных состояния: «проблем не найдено», «частичный результат», «не тот формат» | 3 экрана, можно упрощённо |
| 3:45–4:00 | Причесать, отдать в Figma с названными слоями | Ссылка разработчикам |

**Если время горит — режем в этом порядке:** сначала красивые состояния ошибок (3:15–3:45), потом раскрытый вид доказательств. Экран отчёта и стайл-тайл не режем никогда.

**Чего точно не делаем:** графики, диаграммы, иллюстрации, лендинг, логотип, анимации, мобильная версия, тёмная+светлая темы (выбери одну — лучше тёмную).

## 1. Что это за продукт (в одном абзаце)

Пользователь загружает лог-файл сессии AI-кодинг-агента (Claude Code, `.jsonl`). Сервис разбирает его и показывает: **где агент ходил по кругу, на чём терял время и токены, и какие правила добавить в проект, чтобы в следующий раз так не было**. Ценность — не дашборд с графиками, а **проверяемая цепочка**: находка → конкретные шаги лога как доказательство → рекомендация → скачиваемый текст правила.

Аудитория: разработчики. Тон — спокойный, инженерный, без «AI-магии» и маркетинговых градиентов. Плотная информация, но читаемая. Показывать будем на проекторе — крупный текст важнее изящества.

---

## 2. Главный принцип (важнее всего остального)

В интерфейсе должны **визуально различаться три типа информации**. Это требование продукта, не косметика:

| Тип | Что это | Пример |
|---|---|---|
| **Факт** | Посчитано кодом, всегда проверяемо | «Bash `npm test` вызван 3 раза, все 3 — ошибка» |
| **Гипотеза** | Сказала языковая модель, может быть неверна | «Вероятно, агент не проверил доступные команды проекта» |
| **Нет данных** | Поля нет в логе | «Стоимость неизвестна» |

Нужны три разных визуальных регистра (цвет / иконка / фон / подпись). Если по экрану непонятно, где факт, а где догадка — продукт теряет смысл.

Два следствия:

1. **`null` ≠ `0`.** «Токены неизвестны» и «0 токенов» выглядят по-разному. Никогда не рисуем `0` там, где данных просто нет.
2. **«Значимых проблем не найдено» — нормальный результат**, а не ошибка и не пустой экран.

## 3. Экран 1. Загрузка + обработка

Один артборд, три состояния.

### Состояние A — пусто
- Зона выбора / перетаскивания файла `.jsonl`
- Подсказка, где лежит файл: `~/.claude/projects/<проект>/<uuid>.jsonl`
- **Предупреждение о приватности**: фрагменты лога уйдут в облачный API модели; секреты маскируются, но гарантии нет
- **Переключатель «анализ без отправки в облако»** — равноправная опция, не мелкий серый текст
- Лимит: до 50 МБ

### Состояние B — обработка
Может идти десятки секунд. Спиннер не годится — нужно объяснять, что происходит.
- **5 стадий подряд**: чтение файла → расчёт метрик → подготовка доказательств → объяснение моделью → сборка отчёта
- Процент показываем **только там, где он честный** (байты, «пакет 3 из 8»). На остальных стадиях — индикатор без цифр. Нарисуй оба варианта.
- Предупреждения копятся списком по ходу («строка 42 повреждена»), не блокируют

### Состояние C — ошибка загрузки
Не тот формат / пустой файл / слишком большой. Текст конкретный: «Поддерживается Claude Code JSONL».

## 4. Экран 2. Отчёт — главный

### 4.1. Шапка
- Итог в 1–2 предложения
- **Статус анализа**, 4 варианта (нужны 4 бейджа):
  - `complete` — всё посчитано
  - `partial` — «объяснено 8 находок из 12» + причина
  - `insufficient_data` — данных мало для выводов
  - `failed` — не смогли
- Покрытие: распознано шагов, битых строк, неизвестных событий
- Кнопки скачивания: `report.md`, `report.json`, `CLAUDE.generated.md`

### 4.2. Метрики
Метрика — это не просто число, а **число + единица + ограничение**. В карточке должно быть место под сноску.

Что выводим:
- Шагов, вызовов инструментов, сообщений человека
- Ошибки — **обязательно со знаменателем**: «3 из 12 вызовов с известным статусом», рядом «статус неизвестен: 4»
- Токены исходной сессии агента (input / output / cache), с пометкой если часть неизвестна
- **Отдельно и явно отделено** — расход нашего собственного анализа. Эти два числа нельзя ставить рядом без разделения и нельзя складывать.
- Стоимость — **может быть неизвестна**. Нужен вид «стоимость неизвестна, вот токены».
- Временной диапазон сессии

### 4.3. Находки — сердце отчёта

Список карточек по убыванию приоритета: **высокий / средний / низкий** (нужна визуальная шкала).

Шесть типов находок — нужны иконки или цветовые категории:
1. Повторяющиеся вызовы одного инструмента
2. Ошибки и серии повторных попыток
3. Дорогие по токенам участки
4. Вмешательства человека
5. Отменённые правки (`A → B → A`)
6. Длинные паузы между шагами

Содержимое карточки (свёрнутый вид):
- Тип + приоритет
- **Оценка модели**: `inefficient` / `reasonable` / `uncertain` — три состояния, `uncertain` не должен выглядеть как провал
- **Наблюдение** (факт кода): «Bash `npm test` вызван 3 раза, все 3 раза ошибка `Missing script: test`»
- **Возможная причина** (гипотеза модели) — визуально отличается от наблюдения
- **Рекомендация**: действие + как проверить пользу + готовый текст правила с кнопкой «копировать»
- **Ограничения**, если есть: «контекст был усечён», «релевантного изменения между попытками не обнаружено»
- Пометка происхождения: объяснено моделью (`llm`) или шаблон (`rule_based`)
- Кнопка «Показать доказательства (6 шагов)»

### 4.4. Предупреждения парсера
Сворачиваемый блок внизу: битые строки, оборванный конец файла, неизвестные типы событий.

## 5. Раскрытый вид: доказательства внутри карточки

Вместо отдельной страницы. Раскрывается прямо в карточке находки.

- Лента шагов с нумерацией и **номером строки в исходном файле**
- Типы шагов — визуально разные: сообщение человека, текст агента, вызов инструмента, результат инструмента, системное/неизвестное событие
- Вызов инструмента: имя (Bash, Edit, Read…) + команда моноширинным
- Результат: успех / ошибка / **статус неизвестен** (третье состояние обязательно)
- Время шага (может отсутствовать), интервал до предыдущего шага
- Шаги-доказательства этой находки — подсвечены
- Длинные выводы инструментов (бывают мегабайты) — свёрнуты, «показать полностью»

## 6. Обязательные состояния (нарисовать, даже грубо)

- **«Значимых проблем не найдено»** — уверенный позитивный экран, не пустота
- **Модель недоступна** — метрики есть, объяснений нет, честная пометка
- **Не тот формат файла** — «Поддерживается Claude Code JSONL», а **не** «проблем не найдено»
- **Значение неизвестно** (`—`) — в любом месте, где обычно число

Ниже приоритет, если останется время: анализ прерван рестартом («повторить»), в файле несколько сессий (выбор).

---

## 7. Чего НЕ нужно

- Графики, диаграммы, «красивая аналитика» ради вида
- Регистрация, история загрузок, сравнение сессий, настройки
- Проценты уверенности вроде «93% точность» — мы их не измеряем
- Обещания «сэкономлено 40% бюджета» — таких данных у нас нет
- Логотип, лендинг, онбординг, анимации, мобильная вёрстка

---

## 8. Дизайн-система: минимум

- Одна тема, желательно тёмная. Моноширинный шрифт для команд, кода и логов.
- Плотная сетка, но чёткая иерархия. Демо на проекторе — крупный основной текст.
- Компоненты, которые точно нужны (и только они):
  1. Бейдж «факт / гипотеза / нет данных»
  2. Бейдж статуса анализа (4 вида)
  3. Карточка метрики (с местом под ограничение)
  4. Карточка находки (свёрнутая + раскрытая)
  5. Строка шага лога (5 типов, 3 статуса)
  6. Блок кода с кнопкой «копировать»
  7. Кнопка, поле загрузки, переключатель

Называй слои по-человечески — разработчики будут собирать React-компоненты один в один по этим именам.

---

## 9. Одна фраза, которую надо держать в голове

> «Код нашёл факты, модель объяснила, пользователь может кликнуть и проверить каждое утверждение».

Дизайн должен делать эту цепочку очевидной с первого взгляда. Всё, что этой цепочке не служит, — режем.
