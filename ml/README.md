# Наша ML-часть: от доказательств к объяснению

Здесь находится отдельный Python-модуль для нашей роли в команде. Он получает факты и фрагменты истории, отправляет их модели с промптом и возвращает проверенный JSON. Пакет уже подключён к общему HTTP backend; запуск всего проекта описан в [корневом README](../README.md).

После уточнения заказчика у нас три приоритета:

- **Повторы без прогресса.** Код выделяет серии от трёх одинаковых последовательных вызовов с одинаковыми результатами. Модель оценивает, оправдан ли повтор по видимому контексту. Ожидание сервиса может быть нормальным; повтор после правки — отдельная попытка.
- **Возможность упростить работу.** Пока ищем серии чтения разных файлов. Предлагаем проверить более узкий поиск; конкретный инструмент называем только при наличии его вызова и успешного результата в этом эпизоде. Это гипотеза для проверки, а не доказательство оптимального решения.
- **Проблемы только из лога.** Фактические формулировки создаёт код. Модель выбирает готовые факты, оценку и допустимый совет, подтверждая факты точными цитатами. Выдуманный текст проблемы или причины не входит в контракт ответа.

Мы анализируем завершённую сессию. Самого исходного агента этот модуль не останавливает: он показывает, где проверить повторы, и предлагает правило на будущее. У нашего анализатора отдельно ограничены время и число обращений к модели.

Начинаем с **локального предпросмотра без ключа**, затем подключаем реальный API. Docker запускает наш Python-код. Сама GPT работает у провайдера, поэтому GPU внутри контейнера не нужен.

## 1. Нужно ли давать модели примеры логов

Разделяем три вещи:

- **Логи для разработки и проверки нужны.** Мы смотрим их структуру, вручную отмечаем проблемы и проверяем качество рекомендаций.
- **Для каждого разбора нужны данные конкретной сессии.** Backend выбирает эпизоды и передаёт их нашему модулю. Без них модель не знает, что произошло.
- **Загружать весь архив модели как обучающий материал не нужно.** Мы не обучаем модель. В первом промпте нет посторонних сессий как примеров. Позже можно добавить один короткий размеченный пример, если проверка покажет пользу.

Предоставленный `logs.zip` содержит 97 JSONL-файлов с записями Claude Code. Архив нужен локально для проверки; он не включён в git и Docker-образ. Полный архив в облако не отправляется.

`examples/packet.json` — маленький синтетический пример нашего входного контракта. Это не реальная сессия и не материал для демонстрации качества на защите.

## 2. Что получает и возвращает наш модуль

```text
Backend: парсер + метрики + выделение эпизодов
    ↓ ReviewInput: задача, кандидаты, факты, шаги-доказательства
Наш review_async(): маскирование → сжатие → лимит размера → промпт + API
    ↓ проверка фактов и цитат по исходному подготовленному эпизоду
    ↓ ReviewReport: факты, объяснения, рекомендации, ограничения
Backend сохраняет результат → frontend показывает его пользователю
```

**Кандидат** — эпизод, который стоит проверить. Ошибка инструмента ещё не означает плохую работу агента.

Общий backend использует основной парсер и детекторы из `src/analysis/`. Адаптер `src/reports/builder.py` передаёт их сигналы как `detector_observation` с фактами и цитатами; этот тип допускает оценку `uncertain` или `reasonable` и совет `inspect_observation`. Вспомогательный `prepare.py` ниже нужен только для отдельной разработки ML, сервер его не вызывает.

Каждый кандидат содержит:

- `candidate_id`: уникальный ID эпизода;
- `kind`: тип наблюдения;
- `priority`: приоритет эпизода; сначала обрабатываем high, потом medium и low;
- `task_context`: актуальная просьба пользователя для этого эпизода;
- `facts`: объекты с `fact_id`, готовым текстом и `evidence_step_ids`; их устанавливает backend кодом;
- `evidence`: шаги с `step_id`, типом, текстом и при наличии номером строки;
- `alternatives`: инструменты, применение которых подтверждено вызовом и результатом;
- `context_complete`: достаточно ли прямого контекста эпизода для строгой оценки; при пропусках или усечении — false;
- `limitations`: что нам неизвестно или было усечено.

Модель возвращает `ModelDecision`: `assessment=inefficient|reasonable|uncertain`, выбранные `fact_ids`, `citations` с точными цитатами, `advice` из фиксированного списка и при необходимости `alternative_id`. Код проверяет, что все выбранные факты подтверждены ссылками и цитатами, а совет подходит к типу эпизода.

Затем `grounding.py` собирает `Judgment`: `explanation` из готовых фактов, `action` и `verification` из шаблонов. `likely_cause` всегда null: свободные предположения о причинах отключены. Правило `rule_text` появляется только для повторов, оценённых как неэффективные при достаточном контексте; автоматически оно не применяется.

**Контракт обновлён до `schema_version: "2"`.** Старые подготовленные JSON нужно заново получить командой `prepare`. Backend должен передавать факты с доказательствами, а не прежний массив строк. Входные факты — зона ответственности парсера/backend: схема проверяет ссылки, но не доказывает истинность произвольного текста, который кто-то положил в `facts`.

Оценка `inefficient` остаётся интерпретацией модели. Точная цитата доказывает наличие текста в логе, но сама по себе не доказывает правильность оценки. В интерфейсе нужно сохранять это различие и показывать ограничения.

`complete` означает, что все переданные кандидаты получили валидный ответ. Это **не** гарантия полноты анализа всей сессии. `partial` означает, что некоторые объяснения пропущены или не прошли проверку. `no_candidates` означает отсутствие переданных кандидатов, а не доказанную эффективность агента.

### Сжатие между детектором и моделью

Порядок такой: **парсер → детектор → маскирование → compression.py → модель → проверка**. Детектор сначала определяет факты и выделяет эпизод. Сжатие затем уменьшает представление этого эпизода для модели; отдельного вызова нейросети для сжатия нет.

Что убираем из запроса:

- Повторяющиеся тексты. Первый текст оставляем целиком, следующие точные копии заменяем на `text_ref` — ID предыдущего шага с тем же текстом. Сохраняем каждый шаг, его тип, ID и порядок. Короткий текст оставляем как есть, если ссылка получилась бы длиннее.
- Дублирование задачи: актуальная просьба передаётся один раз в `task`.
- Служебные `source_id`, `source_line` и `priority`: они остаются в исходном пакете и отчёте. Модель использует `step_id`, по которому backend находит строку лога.
- Пробелы между полями JSON. Пробелы, переводы строк и отступы **внутри** текстов лога сохраняем точно.

Например, два шага с одинаковым длинным сообщением об ошибке передаются так:

```json
[
  {"step_id":"step-2","kind":"tool_result","text":"is_error=true; Missing script: test"},
  {"step_id":"step-4","kind":"tool_result","text_ref":"step-2"}
]
```

Это по-прежнему два отдельных результата. Модель должна подтвердить каждый нужный шаг его собственным ID. `grounding.py` проверяет цитату по тексту в исходном подготовленном пакете, где текст каждого шага сохранён полностью.

Сжатие не удаляет уникальные ошибки, успешные результаты, команды, правки, пояснения агента, факты и ограничения. Успех между ошибками или правка между повторами могут полностью изменить оценку. Не заменяем такие данные свободным пересказом.

**Граница обещания «без потерь»:** все тексты и связи уже подготовленного эпизода восстанавливаются точно. Сам helper `prepare.py` раньше выбирает только часть истории и обрезает длинные тексты с `[TRUNCATED]`; это отдельное ограничение, которое сжатие не скрывает и не исправляет. Исходный JSONL/ZIP остаётся локально. Если после сжатия запрос всё равно больше лимита, кандидат получает `request_too_large`; компрессор не вырезает ещё куски доказательств.

В `preview` есть список `compression`, в отчёте — `findings[].compression` для эпизодов, которым собран запрос. Он показывает размеры JSON входа до и после (`original_input_bytes`, `compressed_input_bytes`), сэкономленные байты, число ссылок вместо повторов и число сохранённых шагов. Это **байты данных, без промпта и схемы**, а не число токенов или обещанная экономия денег. Проверка общего лимита учитывает также промпт и схему.

Входной контракт backend остаётся версии 2. Backend передаёт обычные `evidence.text`, сжимать их самостоятельно не нужно: `preview` и `review_async` вызывают один и тот же компрессор автоматически.

## 4. Выбор модели

Начальный вариант — **`gpt-4.1-mini-2025-04-14`**. На входе уже есть факты и небольшой эпизод, а задача модели ограничена выбором оценки, доказательств и совета. Это отправная точка для проверки, а не доказательство достаточного качества на этих логах.

Для сравнения предусмотрена **`gpt-4.1-2025-04-14`**. Обе модели поддерживают Responses API и Structured Outputs. По проверенным 20 сентября 2026 года стандартным тарифам mini стоит $0.40/$1.60 за миллион входных/выходных токенов, полная GPT-4.1 — $2/$8. При одинаковом числе обычных токенов разница пятикратная. Источники: [GPT-4.1 mini](https://developers.openai.com/api/docs/models/gpt-4.1-mini), [GPT-4.1](https://developers.openai.com/api/docs/models/gpt-4.1).

Пример расчёта: 10 000 входных + 1 000 выходных токенов стоят примерно $0.0056 для mini и $0.028 для полной модели, без скидок кэша и дополнительных услуг. Реальный запрос может быть другого размера; расход сохраняется в `analysis_usage`.

Большая модель нужна, **если на одинаковых данных она заметно лучше отличает оправданные действия от бесполезных повторов, выбирает доказательства и применимые советы**. Размер сам по себе не решает ошибки парсера или недостаток контекста. Сначала проверяем mini на размеченных эпизодах; затем меняем `--model` и сравниваем ответы. Требование «не выдумывать» обеспечиваем ограничением ответа и проверками, а не надеждой на более крупную модель.

Доступ к API, оплату и разрешённость использования из среды развёртывания проверяет команда. Облачный запрос нельзя проверить одним Docker build. Ключ хранится локально в окружении или `.env`, в чат и git его не отправляем.

## 5. Первый запуск без Docker и без API-ключа

Из корня репозитория:

```bash
cd ml
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
python -m agent_review preview examples/packet.json --out output/preview.json
```

Открываем `output/preview.json`. Там точный промпт, данные кандидата, модель и JSON-схема ожидаемого ответа. **Это предпросмотр запроса, а не ответ нейросети.** Денег и ключа не требует.

`preview` и `explain` читают один и тот же контракт. В рабочей версии backend передаст такой объект в Python-функцию напрямую, без промежуточного файла.

## 6. Проверка на нашем архиве

Команды выполняем из `ml/`. На macOS путь к предоставленному архиву:

```bash
python -m agent_review list-logs "$HOME/Desktop/logs.zip"
```

Выбираем одну строку `member` из списка. Например, этот файл действительно присутствует в архиве:

```bash
python -m agent_review prepare "$HOME/Desktop/logs.zip" \
  --member 'raw-logs/-Users-egor-Downloads-web-server-2/fb56f630-6ef7-4159-86d6-e270bee1036a.jsonl' \
  --out output/real-packet.json

python -m agent_review preview output/real-packet.json \
  --max-calls 1 --out output/real-preview.json
```

Можно передать обычный `.jsonl` вместо ZIP; тогда `--member` не нужен. ZIP читается без распаковки и без запуска содержимого.

Helper выделяет три типа кандидатов: `explicit_tool_error`, `repeated_tool_call`, `read_many_files`. Повторы сравниваются по полным аргументам и результатам до маскирования. Другой инструмент, новая просьба человека, разрыв цепочки или неизвестная запись прерывают серию. Параллельные вызовы не считаются повторными попытками. В доказательства добавляются доступные пояснения агента; если их пришлось сократить, строгая оценка неэффективности запрещена.

Серии чтения — только повод проверить способ поиска. Наличие трёх чтений не доказывает проблему. Утилита для альтернативы берётся из ранее наблюдавшегося в том же эпизоде вызова Grep/Glob либо простой команды rg/grep/find с явно успешным результатом.

Helper нужен, чтобы ML-разработка не ждала полного backend. Он не считает стоимость исходной сессии, не распознаёт все смысловые циклы и чередования нескольких команд, не реализует все направления кейса и не заменяет производственный парсер. Отсутствие кандидатов сопровождается предупреждением и не означает доказанную эффективность.

Самостоятельно просматриваем подготовленные доказательства. Маскирование известных секретов есть, но не гарантирует удаления всей чувствительной информации. Перед `explain` нужно убедиться, что выбранные фрагменты можно отправлять провайдеру. Это особенно важно для чужих логов и закрытого кода.

## 7. Настоящий запрос к модели

Для локального Python задаём ключ в окружении, например через безопасное поле настроек IDE/терминала. CLI сам не читает `.env`; этот файл автоматически подхватывает Docker Compose.

После установки `OPENAI_API_KEY` запускаем:

```bash
python -m agent_review explain examples/packet.json \
  --max-calls 1 --out output/report.json
```

Для своего эпизода вместо `examples/packet.json` указываем `output/real-packet.json`. Это платный сетевой запрос. `explain` не обучает модель и не загружает архив в постоянную базу знаний.

Проверка более крупной модели на тех же данных:

```bash
python -m agent_review explain output/real-packet.json \
  --model gpt-4.1-2025-04-14 \
  --max-calls 1 --out output/report-large.json
```

Сравниваем с ответом mini вручную: верна ли оценка, не назван ли оправданный повтор неэффективным, уместен ли совет, подтверждают ли цитаты выбранные факты. Одного успешно разобранного JSON недостаточно, чтобы утверждать качество модели.

## 8. Запуск через Docker

Запускаем Docker Desktop. Все команды ниже из `ml/`:

```bash
mkdir -p data output
docker compose build
docker compose run --rm ml
```

Последняя команда запускает безопасный предпросмотр учебного примера. Результат появляется **на нашем компьютере** в `ml/output/preview.json`.

В [compose.yaml](compose.yaml) две подключённые папки: `data/` видна контейнеру как `/data` только для чтения, `output/` — как `/output` для результатов. Образ содержит код, зависимости, синтетический пример и тесты. Наши реальные логи и `.env` в образ не копируются. [Docker: bind mounts](https://docs.docker.com/engine/storage/bind-mounts/).

Для настоящего архива:

```bash
cp "$HOME/Desktop/logs.zip" data/logs.zip
docker compose run --rm ml list-logs /data/logs.zip
docker compose run --rm ml prepare /data/logs.zip \
  --member 'raw-logs/-Users-egor-Downloads-web-server-2/fb56f630-6ef7-4159-86d6-e270bee1036a.jsonl' \
  --out /output/real-packet.json
docker compose run --rm ml preview /output/real-packet.json \
  --max-calls 1 --out /output/real-preview.json
```

Чтобы включить API:

```bash
cp .env.example .env
```

Открываем `.env` у себя и вписываем ключ в `OPENAI_API_KEY`. Затем:

```bash
docker compose run --rm ml explain /output/real-packet.json \
  --max-calls 1 --out /output/report.json
```

Для полной модели добавляем `--model gpt-4.1-2025-04-14` либо меняем `LLM_MODEL` в `.env`. Пересборка образа для смены модели не нужна. После изменения Python-кода или промпта выполняем `docker compose build` снова.

Этот контейнер выполняет команду и завершается; порты и отдельный HTTP-сервер для него не нужны. Команда backend может установить пакет в свой Docker-образ и вызывать функцию из фонового обработчика. Два контейнера не вызывают Python-функции друг друга напрямую: для отдельного постоянно работающего ML-сервиса backend должен добавить HTTP/очередь. Сейчас выбираем более простой вариант с библиотекой.

## 9. Что передать backend-разработчику

Контракт находится в `schemas.py`, пример — в `examples/packet.json`. Установка пакета из корня общего проекта:

```bash
python -m pip install ./ml
```

В его Python-коде:

```python
from agent_review import ReviewInput, review_async

# payload backend формирует из своих парсера, метрик и найденных эпизодов.
packet = ReviewInput.model_validate(payload)
report = await review_async(packet, max_calls=8)
result_for_frontend = report.model_dump()
```

Этот фрагмент выполняется внутри async-функции backend. `review_async` ожидает сеть без блокировки event loop и поддерживает отмену. Для обычного синхронного worker/CLI есть `review(packet, max_calls=8)`. Вызов `review` из async-обработчика выдаёт понятную ошибку; там нужен `await review_async`. Управление пользователями, файлами, БД, очередями и сохранением результатов остаётся у backend.

Наш модуль сортирует кандидатов по `priority`, сохраняя исходный порядок внутри одного приоритета. Backend может дополнительно ранжировать их до передачи. При лимите обрабатываются первые помещающиеся кандидаты; остальные остаются в результате с причиной пропуска. Frontend не должен выдавать `uncertain`, пропущенный кандидат или одиночную ошибку за подтверждённую проблему.

## 10. Ограничения этой простой версии

- Один кандидат на один запрос, максимум восемь запросов за вызов `review`.
- До 48 000 байт на промпт + сжатые данные + схему. Это консервативный бюджет размера, **не точный подсчёт токенов**. Лимит проверяем после сжатия. Слишком большой кандидат пропускается явно; доказательства не обрезаются молча.
- До 4 000 выходных токенов, до 30 секунд на запрос и общий бюджет анализа 120 секунд. Ожидание запроса отменяется при исчерпании бюджета; остальные кандидаты получают причину пропуска. К этому добавляются локальная обработка и до секунды закрытия собственного клиента. Запросы последовательные, SDK-повторы отключены. При ошибке доступа, лимита провайдера или соединения остальные запросы не запускаются.
- Отказ модели, таймаут, неверные ссылки или неполный ответ дают `partial`; подтверждённого объяснения в таком пункте нет. Сервис не подменяет его выдуманным ответом.
- `analysis_usage` относится к **нашему анализу**, а не к расходу агента из загруженного файла.
- `store=False` используется при вызове API, но не является обещанием нулевого хранения любых данных провайдером.
- Структура ответа проверяется кодом; правильность смысла всё ещё проверяется по доказательствам и размеченным примерам.
- Возвращаем `rule_text`, не применяем его к репозиторию. Файловый экспорт правил может сделать backend.

Для `explain` код завершения `0` — обработка завершена или кандидатов нет, `2` — сохранён частичный отчёт, `1` — ошибка входа/настройки. Автоматизация должна проверять также поле `status`.

## 11. Проверки

Без API и денег:

```bash
python -m unittest discover -s tests -v
```

В контейнере:

```bash
docker compose run --rm --entrypoint python ml -m unittest discover -s tests -v
```

Тесты проверяют повторы и оправданные изменения между попытками, контекст разных задач, дубликаты и повреждённые записи, ложные цитаты, недоступные инструменты, контракт, маскирование, лимиты, отмену зависшего запроса и ошибки API. Один тест использует настоящий OpenAI SDK с подставленным HTTP-ответом: проверяется интеграционный формат, запрос в интернет не отправляется. Это не оценка качества живой модели.

Подготовка и предпросмотр обработали все **97 файлов** предоставленного архива без падений: 12 466 записей, 80 явных ошибок инструментов и 35 эпизодов чтения нескольких файлов. Это 115 кандидатов для проверки, а не 115 доказанных проблем. Подготовлены 114 запросов предпросмотра; один кандидат пропущен из-за лимита числа запросов на сессию. Строгий детектор одинаковых повторов кандидатов на этом архиве не выделил; его положительные и отрицательные случаи проверены синтетическими тестами. Это не доказывает отсутствие более сложных циклов в архиве.

После добавления сжатия прошли **52 теста локально и в Docker**. Проверка всех 115 кандидатов восстановила из сжатого представления все 681 шага: тексты, ID, типы и порядок совпали с подготовленными эпизодами. Объём JSON данных уменьшился с 724 569 до 646 448 байт, на **10,78%**. Здесь считаются все кандидаты, включая пропущенный по лимиту вызовов; промпт, JSON-схема и токены в эту цифру не входят. Выигрыш на другом наборе логов будет отличаться.

Живой вызов модели пока не выполнялся: API-ключ не настроен. Поэтому проверены код и интеграционный формат, но точность классификации на настоящем API ещё не измерена.

Для оценки качества отбираем несколько настоящих эпизодов: явное повторение ошибки, разумный повтор после правки, ошибка среды, эпизод с недостатком данных. Заранее записываем ожидаемую интерпретацию и допустимые рекомендации. Одни эпизоды используем для настройки промпта, другие оставляем для финальной проверки.

Официальный механизм ответа по схеме: [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs). Промпт и проверки в этом модуле — наша реализация, её качество на живом API ещё нужно измерить.
